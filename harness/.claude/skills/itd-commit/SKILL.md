# ITD Commit

## Overview

입력받은 티켓 제목과 현재 브랜치 정보를 조합해 ITD 티켓 커밋 컨벤션에 맞는 메시지를 생성하고 커밋한다. 티켓 종류/번호는 사용자에게 묻지 않고 **현재 브랜치명에서 자동 추출**한다.

## 브랜치 전략 - 1 branch 1 commit

`docs/agent-rules/project.md`의 커밋 절에 "1 branch 1 commit"이 적힌 프로젝트는 **하나의 feature/fix 브랜치(`feat/ITD-###`, `fix/ITD-###`)에 커밋을 1개만 유지**한다. 적혀 있지 않으면 이 절을 건너뛰고 브랜치에 커밋을 쌓는다.

- 해당 브랜치에 **아직 커밋이 없으면** 신규 커밋(Workflow)으로 진행한다.
- 해당 브랜치에 **이미 커밋이 하나라도 있으면**, 새 커밋을 쌓지 않고 항상 `git commit --amend`(Amend 절차)로 그 커밋에 합친다. "커밋해"류 요청도 이 판단 기준(브랜치에 커밋 존재 여부)을 먼저 확인한 뒤 신규/amend를 스스로 정한다 - 사용자가 "amend해"라고 명시하지 않아도 브랜치에 커밋이 있으면 amend가 기본 동작이다.
- 브랜치에 커밋이 여러 개 이미 쌓여 있는 상태(과거에 이 원칙 없이 커밋된 경우 등)를 발견하면, 임의로 `git rebase -i`나 squash를 실행하지 않고 사용자에게 상황을 보고하고 정리 방식을 확인한다.
- 판단 방법: `git log --oneline <base-branch>..HEAD` (base는 `docs/agent-rules/branch-strategy.md`의 통합 브랜치, 프로젝트가 다르게 정했으면 `project.md` 값)로 이 브랜치에만 있는 커밋 수를 센다. 1개면 amend 대상, 0개면 신규 커밋 대상.

## 커밋 컨벤션

### 제목 (첫 줄)

```
{종류}/{티켓번호} {티켓 제목}
```

- `종류`: 브랜치명의 슬래시 앞부분 (`feat` · `fix`)
- `티켓번호`: 브랜치명의 `ITD-###` 부분
- `티켓 제목`: 사용자가 입력한 문자열 그대로 사용 (임의 접두어 추가/삭제 금지)

예: 브랜치 `feat/ITD-6838` + 입력 `프로젝트 스캐폴딩` → `feat/ITD-6838 프로젝트 스캐폴딩`

제목과 본문 사이에 빈 줄 1개를 넣는다. Git 컨벤션상 첫 줄=subject, 그다음 빈 줄, 이후=body이며, 빈 줄이 없으면 GitLens 등 도구가 제목/본문을 구분하지 못한다.

### 본문 - `feat`

제목 다음 빈 줄 뒤에 작업 내용을 bullet(`- `) 리스트로 나열한다. staged diff를 근거로 실제 변경 사항만 작성한다.

**추상화 수준**: 파일·심볼 단위로 일일이 나열하지 말고 의미 단위로 묶어 요약한다. 여러 파일에 걸친 같은 성격의 변경은 하나의 bullet로 통합하고, "무엇을 왜 했는지"가 드러나게 쓴다. bullet 개수는 변경 규모에 맞추되 통상 3~7개 수준으로 압축한다.

**제외 대상**: staged된 경로 그룹을 기계적으로 bullet로 옮기지 않는다. 코드/제품 의미가 없는 변경은 본문에서 뺀다 - orchestrator 작업 노트(`artifacts/00~05*` 등), 포맷터/린터 자동 수정, lockfile 갱신 등. "○○ 파일 갱신"처럼 무엇을 왜 했는지가 없는 bullet은 쓰지 않는다.

```
feat/ITD-6838 프로젝트 스캐폴딩

- Next.js 16 + TypeScript + React Query + Tailwind 기본 구조 세팅
- client/server axios 이원화 및 proxy.ts 인증 처리 추가
- eslint/biome 설정 및 폴더 구조(services/hooks/components) 정리
```

### 본문 - `fix`

제목 다음 빈 줄 뒤에 `- 원인:` 과 `- 해결:` 을 각각 한 줄 bullet로 작성한다.

```
fix/ITD-6900 로그인 후 쿠키 만료 시간이 반영되지 않는 문제 수정

- 원인: cookie.ts의 만료 시간 상수가 초 단위인데 밀리초로 계산해 실제 만료 시간이 1000배 길어짐
- 해결: 만료 시간 계산 로직을 초 단위 기준으로 통일
```

## Workflow

1. **브랜치 확인·파싱**: `git rev-parse --abbrev-ref HEAD` 로 현재 브랜치를 얻고 `{종류}/{ITD-번호}` 로 분해한다.
   - 패턴(`^(feat|fix)/ITD-\d+`)에 맞지 않으면(`main`, `develop` 등) 커밋을 진행하지 않고 사용자에게 보고한다. main/develop 직접 커밋은 금지.
2. **변경 사항 확인**: `git status` 와 `git diff --staged` 를 확인한다.
   - staged 변경이 없으면 `git diff`(unstaged)를 보고, 어떤 파일을 stage할지 사용자에게 확인한다. 임의로 `git add .` 하지 않는다.
   - staged 파일에 티켓 범위와 무관해 보이는 파일(`.claude/`, 설정 파일, 다른 도메인 등)이 섞여 있으면, 임의로 포함/제외하지 말고 전체 staged 목록을 보여주고 무엇을 이 커밋에 넣을지 사용자에게 확인한다.
3. **본문 구성**: diff를 근거로 본문을 작성한다.
   - `feat`: 변경을 의미 단위로 묶어 bullet 리스트 작성 (파일 나열이 아닌 "무엇을 했는지" 기준).
   - `fix`: 원인 한 줄 + 해결 한 줄. diff만으로 원인이 불명확하면 추측하지 말고 사용자에게 원인을 확인한다.
4. **메시지 미리보기**: 완성된 커밋 메시지 전문을 보여주고 **응답을 종료한다(멈춘다)**. 같은 응답에서 이어서 `git commit` 을 실행하지 않는다. 사용자 요청이 "커밋 메시지 만들어줘"처럼 메시지 생성만 원하는 경우도 여기서 종료한다.
   - `Co-Authored-By` 트레일러나 기타 자동 서명은 ITD 커밋 형식에 없으므로 추가하지 않는다.
5. **커밋 실행**: `git commit` 실행은 메시지 생성·미리보기와 분리된 별도 툴 호출로 한다.
   - **아직 미리보기를 한 번도 제시하지 않은 상태**의 "커밋해", "다시 커밋해", "ㄱㄱ" 발화는 작업 지시일 뿐 승인이 아니다 - 미리보기부터 만들고 멈춘다.
   - **직전 또는 그 이전 턴에 이미 같은 메시지를 미리보기로 제시했고 그 뒤 내용이 바뀌지 않았다면**, "커밋해"·"다시 커밋해"·"진행해"는 그 미리보기에 대한 승인이다 - 미리보기를 다시 붙여넣고 또 멈추지 말고 그 턴에 바로 실행한다.
   - `git push` 는 이 스킬 범위 밖 - 사용자가 별도로 요청할 때만 실행한다.

## Amend / 기존 커밋 수정

"amend해", "직전 커밋에 합쳐", "이 커밋에 합쳐줘", "fixup", "squash", "메시지 다시 써" 같은 요청은 **신규 커밋이 아니라 기존 커밋 수정**이다. 이때도 이 스킬을 거친다.

1. **대상 커밋 확인**: `git log -1 --format='%H %s'` 로 HEAD를 확인하고, 사용자가 지정한 커밋 해시와 HEAD가 같은지 본다. HEAD가 아니면(중간 커밋 대상) 사용자에게 rebase 필요 여부를 확인하고, 임의로 `git rebase` 하지 않는다.
2. **브랜치 확인·파싱**: Workflow 1단계와 동일. main/develop면 중단.
3. **합산 변경 확인**: `git show --stat HEAD` (기존 커밋의 변경) + `git diff --staged` (새로 stage된 변경)를 함께 본다. staged가 없거나 티켓 범위 밖 파일이 섞였으면 Workflow 2단계처럼 확인한다.
4. **본문 재작성**: 기존 커밋 본문을 base로 둔다. 여전히 유효한 기존 bullet은 그대로 보존하고(리워딩·재요약 금지), 신규 staged 변경분에 대한 bullet만 아래에 추가한다. 기존 bullet이 신규 변경으로 더 이상 맞지 않으면 그 줄만 수정한다. 제목은 티켓 제목 기준으로 재조립.
   - 본문 전면 재작성은 사용자가 "본문 새로 써"라고 명시했을 때만.
   - 예외: 사용자가 "메시지는 그대로 두고 파일만 합쳐"라고 **명시**했고, 기존 메시지가 컨벤션에 맞으며 합산 변경까지 포괄하면 `--no-edit` 허용. 이 경우에도 기존 메시지를 먼저 검증해 보고한다.
5. **미리보기**: 재작성된 커밋 메시지 전문을 보여주고 **응답을 종료한다**. 같은 응답에서 `git commit --amend` 를 실행하지 않는다.
6. **amend 실행**: Workflow 5단계와 동일한 승인 기준 - 미리보기 미제시 상태의 "커밋해"는 승인 아님(미리보기부터), 이전 턴에 같은 메시지 미리보기 완료 + 내용 불변이면 "커밋해"·"다시 커밋해"는 승인이므로 재출력 없이 그 턴에 `git commit --amend` 를 heredoc 메시지로 실행한다.

```bash
git commit --amend -m "$(cat <<'EOF'
feat/ITD-6952 통합테스트 Fail Case 수정

- ...
EOF
)"
```

## 커밋 실행 방법

멀티라인 메시지는 heredoc으로 전달한다 (Bash 도구 사용):

```bash
git commit -m "$(cat <<'EOF'
fix/ITD-6900 로그인 후 쿠키 만료 시간이 반영되지 않는 문제 수정

- 원인: ...
- 해결: ...
EOF
)"
```

## 규칙

- 제목과 본문 사이에 **빈 줄 필수** (subject/body 구분).
- 종류/번호는 **브랜치에서만** 추출 - 사용자에게 되묻지 않는다 (제목만 입력받음).
- 본문 bullet은 diff에 실재하는 변경만 기술, 하지 않은 작업 나열 금지. 경로 그룹을 기계적으로 옮기지 말고, 코드/제품 의미 없는 변경(작업 노트·포맷터·lockfile)은 제외.
- 주석/본문 종결 어미는 명사형·비종결 구절 (`~한다.` 금지, `~ 처리`/`~ 추가` 등).
- 브랜치가 feature 브랜치(`feat/ITD-###`, `fix/ITD-###`)가 아니면 즉시 중단하고 보고.
- **1 branch 1 commit**: 브랜치에 커밋이 이미 있으면 신규 커밋을 쌓지 않고 amend가 기본. "커밋해"류 요청도 amend 여부를 먼저 판단한다 (위 "브랜치 전략" 절 참고).
- `git commit` 은 미리보기 후 사용자의 명시적 승인이 있을 때만 실행. `git push` 는 범위 밖으로, 사용자가 별도 요청할 때만.
- `git commit --amend` 도 이 스킬을 거친다. amend 시 본문은 기존 커밋 본문을 base로 두고 신규 staged 변경분 bullet만 추가(유효한 기존 bullet은 리워딩 없이 보존, 안 맞는 줄만 수정). `--no-edit` 은 사용자가 명시적으로 요청한 경우에만.
- 커밋/amend 실행은 메시지 미리보기와 별도 툴 호출로 한다. 미리보기 미제시 상태의 "커밋해"류는 승인 아님(미리보기부터), 이전 턴 미리보기 완료 + 내용 불변이면 "커밋해"류는 승인(바로 실행).
- 어떤 파일을 커밋에 포함할지 애매하면 스스로 정하지 말고 staged 목록을 보여주고 확인한다.
