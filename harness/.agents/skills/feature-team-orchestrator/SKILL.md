# Feature Team Orchestrator

## 목적

이 Orchestrator는 이 프로젝트의 신규 기능 개발을 4개 역할로 나누어 진행한다: 선례 조사 → 계획 → 구현 → 통합 검증.

## 전제 조건

- `docs/agent-rules/project.md`의 "기획·명세 문서"에 PRD 경로가 있다. 기능 요구사항·정책(집계 기준, 판정 기준, 표기 규칙 등) 판단은 이 문서를 1차 근거로 삼는다. PRD가 없으면 사용자 요청 원문을 근거로 삼고 그 사실을 `00-input.md`에 남긴다.
- API 명세 문서의 유무와 위치는 `docs/agent-rules/project.md`를 따른다. 명세에 있는 항목은 실제 연동으로, 명세에 없거나 명세 안에서 미확정인 항목만 목데이터로 진행하고 그 사실을 `02-decisions.md`에 남긴다. 명세가 갱신되면(버전업, 새 엔드포인트) 그 사실을 `00-input.md`에 반영한다.
- `docs/agent-rules/project.md`에 참고 레퍼런스 저장소가 있으면 선례 조사 대상으로 쓴다. 레퍼런스는 참고용 선례이고, 실제 코드를 쓰는 곳은 항상 이 프로젝트다 - 레퍼런스 경로에 파일을 쓰지 않는다.
- Figma 타겟 노드는 매 작업 입력값이다. UI 작업인데 이번 작업 대상 Figma 노드(링크 또는 node-id)가 없으면 `00-input.md`를 쓰기 전에 사람에게 확인한다. 기획서에 적힌 대표 링크는 전체 화면의 시작점일 뿐이므로, 이번 실행에서 다룰 개별 콘텐츠의 하위 노드는 매번 확인한다.
- **Figma 노드 분석은 Orchestrator(메인 세션)가 전담한다.** 팀원은 Figma MCP를 자체 재호출하지 않고, Orchestrator가 저장한 `artifacts/feature-team/00-figma-context.md`를 Read로 읽는다.

## 실행 모드

기본 실행 모드는 Agent Team이다. 선례 조사 결과가 계획 방향을 바꿀 수 있고, 계획 단계의 판단(데이터 계층 구조, 재사용 패턴)이 구현 범위를 바꾸며, 구현 중 발견(목데이터 구조 불일치, 기존 유틸 재사용 가능성 등)이 검증 기준에 영향을 준다. 다만 오타 수정, 스타일 조정처럼 계획·검증이 불필요한 작은 작업은 단일 흐름으로 줄인다.

선례 조사(T02)는 `docs/agent-rules/project.md`에 참고 레퍼런스 저장소가 있고 계획이 필요한 크기의 작업일 때만 실행한다. 레퍼런스 저장소가 없으면 T02를 건너뛰고, spec-planner가 `src/` 기존 코드 조사로 대신한다. 건너뛴 사실은 `00-input.md`에 남긴다.

## 실행 모드 확인

1. `artifacts/feature-team/`에 기존 산출물(`00-input.md`~`04-review.md`)이 있는지 확인한다.
2. 없으면 초기 실행으로 진행한다.
3. 있고 사용자가 "구현만 다시", "계획은 그대로 두고" 같은 부분 수정을 요청하면 해당 단계부터 재실행한다. 이전 단계 산출물은 그대로 입력으로 재사용한다.
4. 완전히 새로운 작업(다른 기능, 다른 화면)이면 기존 산출물을 `artifacts/feature-team/archive/{YYYYMMDD-HHMMSS}/`에 보존하고 새로 시작한다.
5. 사용자 의도가 불분명하면 "이어 하기", "부분 수정", "새 작업" 중 무엇인지 먼저 확인한다.

## Agent Team 실행 흐름

1. 사용자 요청, 이번 실행 범위, 이번 작업의 Figma 타겟 노드, 사람 승인 지점, 선례 조사 실행 여부를 `artifacts/feature-team/00-input.md`에 저장한다. **UI 작업인데 Figma 노드가 없으면 먼저 사람에게 확인한다.** 이전 작업의 전례나 레퍼런스의 처리 방식(범위, 구조, 배치 방식 등)을 이번 작업에 적용할 때는 "가정"이라고 쓰지 않는다 - 전례·레퍼런스는 참고일 뿐 이번 작업에 대한 사람의 승인이 아니므로, `확인 필요(전례 재사용): OO 작업 때는 XX로 처리함, 이번에도 동일하게 볼지 확인 필요`처럼 확인 필요 항목으로 명시한다.
1-1. `00-input.md`에 Figma 노드 링크가 있으면, Orchestrator가 직접 `get_design_context`를 호출해 원문 응답 전체(코드, 스타일 힌트, Component descriptions, 스크린샷 설명 등)를 요약 없이 그대로 `artifacts/feature-team/00-figma-context.md`에 저장한다. 팀원은 이 파일을 Read로 읽어 근거로 삼으며, 자체 MCP 재호출을 전제로 지시하지 않는다.
    **시각적으로 렌더링되는 하위 섹션(카드/컴포넌트 단위)마다 예외 없이 raw 코드 블록을 그대로 보존한다 - 일부만 bullet로 요약하지 않는다.** Figma MCP는 Orchestrator만 호출 가능해 재호출로 복구할 수 없으므로, 한 섹션이라도 요약으로 뭉개면 모든 팀원이 그 손실(색상 변수, 고정 치수 등)을 영구히 놓친다. 저장 직후 `grep -c '```' 00-figma-context.md`로 노드 이름 개수 대비 코드 펜스 개수가 크게 모자라지 않은지 자체 확인한다.
    대상 프레임 서브트리 조회로 끝내지 않는다. 같은 페이지 안에 프레임 밖 별도 좌표로 떨어져 있는 독립 인터랙션/상태 스펙 인스턴스(이름이 `*Tooltip*`, `*Hover*`, `*Dropdown Menu*`처럼 별표로 감싼 placeholder 패턴)가 있는지 확인하고, 있으면 함께 저장한다. 차트/인터랙션 요소가 있는 화면은 이 확인을 생략하지 않는다.
    `get_metadata`가 토큰 제한으로 실패하면 그 노드 전체를 "확인 불가"로 넘기지 않는다. 그 노드에 `get_design_context`를 호출해(경량 XML 메타데이터가 자동 반환되는 경우가 있음) 하위 node-id를 찾고, 그 node-id 단위로 다시 조회해 저장한다.
    이어서 `get_screenshot`을 호출해 실제 Figma 노드 이미지를 받아 `artifacts/feature-team/00-figma-screenshot.png`로 저장한다(다운로드 URL은 발급 후 만료되므로 즉시 저장). integration-reviewer는 이 이미지를 자신이 dev 서버에서 찍은 스크린샷과 나란히 비교할 근거로 삼는다.
    프로젝트가 Tailwind v4를 쓰면 `tailwind.config.ts`의 `content` 설정과 무관하게 프로젝트 전체를 자동 스캔한다. Figma 원문 코드에 `bg-[var(--button\/colorbgcontainer,white)]`처럼 슬래시(`/`)가 포함된 CSS 변수 표기가 있으면 잘못된 임의값 클래스 후보로 파싱되어 빌드 전체가 깨진다(재현 테스트로 확정). 저장 직후 전역 CSS(예: `src/app/globals.css`)에 `artifacts` 디렉터리를 가리키는 `@source not` 줄이 없으면 추가해 이 디렉터리를 스캔 대상에서 제외한다.
    Figma 원문에 범례/배지 그리드처럼 반복 요소가 묶여 있는 하위 프레임이 있으면, `get_design_context`의 코드 힌트만으로는 정확한 폭·줄바꿈 규칙이 드러나지 않을 수 있다(참고 코드가 flex-wrap처럼 보여도 실제로는 고정 px 폭이거나 강제 줄바꿈 단위일 수 있음). 이런 반복 하위 구조가 있으면 `get_metadata`로 그 프레임을 직접 조회해 자식 노드들의 x/y/width를 원문 그대로 `artifacts/feature-team/00-figma-metadata.md`에 저장한다.
    절대 좌표 오버레이, 이미지 crop, `contents` 그룹, 고정 치수처럼 기하 정보가 구현 정확도에 영향을 주면 `artifacts/feature-team/00-figma-geometry.md`에 기준 프레임 노드 ID·크기, 이미지 노드·crop 값, 그룹의 `contents` 여부·실제 좌표 기준, 실제 가시 요소의 기준 위치·크기, 확정하지 못한 항목을 기록한다. 좌표계 또는 crop 기준을 확인할 수 없으면 추측으로 채우지 않고 T03의 사람 승인 필요 항목으로 넘긴다.
    작업 도중 팀원이 저장 파일에 없는 노드를 요청하면(`SendMessage`) 같은 방식으로 원문을 조회해 파일에 추가하고 알린다.
2. 팀원을 스폰하기 전에 `ListAgents`와 `TaskList`/`TaskGet`으로 기존 팀원 존재 여부를 확인한다. 한쪽 결과만으로 "중복 실행이 아니다"라고 단정하지 않고, 스폰 결과의 이름 접미사 발생 여부도 함께 본다.
   - 스폰 프롬프트를 쓰기 전 해당 팀원의 `.codex/agents/{역할}.toml`을 Read로 먼저 확인해서, 그 파일에 이미 규정된 절차와 모순되거나 이를 무효화하는 지시를 프롬프트에 넣지 않는다.
   - `Agent` 도구(`subagent_type`에 팀원 Agent 파일명, `name`에 고정 팀원 이름 지정)로 스폰한다.
   - 스폰 결과 이름이 요청한 이름과 다르면(`-2` 등 접미사) 같은 이름의 생존/stale 세션이 있다는 신호다. 소유권은 `ListAgents`가 아니라 이 세션의 스폰 기록(자신이 스폰 시도했던 이름인지)과 로컬 Task 등록 정보로 판단한다.
     - 이 세션이 스폰한 대상이면 `TaskStop`(`task_id`에 원래 팀원 이름)으로 직접 종료한 뒤 새 이름으로 계속 진행한다.
     - 다른 세션의 크로스세션 피어면 이 세션에 강제 종료 권한이 없으므로 `SendMessage`로 중단을 요청하고, 상대가 idle로 전환됐는지 확인해 중복 수행 여부를 검증한다.
3. `TaskCreate`로 위 Task 등록 계약대로 작업을 등록한다. **이 실행에서 `TaskCreate`는 이 시점 한 번만 호출한다** - 앞선 단계에서 개략적 진행 목록을 별도로 만들지 않는다(동일 subject로 중복 호출 시 기존 태스크와 병합되지 않고 별개 ID로 쌓인다). `TaskCreate`/`TaskUpdate`/`TaskGet`이 없는 환경이면 `artifacts/feature-team/tasks.md`에 위 표를 옮겨 적고, 각 팀원이 자기 행의 상태 칸을 직접 갱신하며, Orchestrator는 이 파일을 다시 읽어 지연을 확인한다.
4. 팀원들은 `TaskUpdate`로 시작, 차단, 완료 상태를 갱신한다.
5. Orchestrator는 Phase 전환 전(T02→T03, T03→T04, T04→T05) `TaskGet`으로 누락과 지연을 확인한다. T04→T05 전환 전에는 `03-implementation-notes.md`에서 "마크업 유지"/"변경 없음" 같은 단정적 서술을 최소 1곳 골라 직접 `git diff`로 스팟체크한다 - integration-reviewer에게 전부 위임하지 않는다.
6. 팀원들은 발견, 질문, 충돌, 도구 미연결, 완료를 `SendMessage`로 공유한다.
7. T03 완료 전, Orchestrator가 `artifacts/feature-team/02-decisions.md`를 직접 열어 확인한다. `유형: 사람 승인 필요`로 표시된 항목마다 `답변:` 필드가 실제로 채워져 있는지 하나씩 확인하고, 비어 있으면 spec-planner가 "확정 완료"로 보고했더라도 그대로 믿지 않는다 - 비어 있는 항목만 골라 사람에게 질문으로 전달하고 답변을 받은 뒤에만 T04로 넘어간다. `유형: 실측 가능` 항목은 spec-planner가 원문·코드 재조회로 해소했는지만 확인한다.
7-1. 비어 있는 "사람 승인 필요" 항목을 사람에게 물을 때는, 질문 전에 **항목마다 현황 보고를 먼저** 한다: 그 결정에 대해 (a) PRD가 무엇을 규정하는지(조항/줄 번호), (b) 레퍼런스가 실제 코드에서 어떻게 처리하는지(`파일:줄`), (c) API 명세가 무엇을 규정하는지, (d) 현재 프로젝트 코드는 어떻게 구현돼 있는지 - 이 네 가지를 표나 목록으로 정리해 제시한 뒤에 옵션을 묻는다. 근거 브리핑 없이 "옵션 1 vs 옵션 2"만 던지지 않는다. 사용자가 "레퍼런스 확인했냐", "왜 또 물어보냐" 같은 반응을 보이면 이 현황 보고 단계를 건너뛴 신호로 보고, 조사 결과를 정리해 보고부터 한 뒤 다시 묻는다.
7-2. Orchestrator는 "사람 승인 필요" 항목의 `답변:` 필드를 **어떤 경우에도 직접 채우지 않는다** - 근거를 충분히 확보했더라도, 사용자가 불만·재촉을 표하더라도, 추천안이 명백해 보이더라도. 근거 수집과 옵션 정리(`조사 근거`/`추천안` 작성)까지가 Orchestrator 몫이고, 옵션 선택은 사람 몫이다. `답변:`은 사람의 명시적 답변으로만 채운다. "추천안"을 "확정"으로 승격하지 않는다. 이 규칙은 `04-review.md`의 "사람 승인 필요" 항목에도 동일하게 적용된다.
7-3. `02-decisions.md`·`02-plan.md`·사용자 보고에 결정의 근거를 적을 때는, 인용하는 각 출처(PRD / API 명세 / 레퍼런스 / 현재 코드)가 그 사항에 대해 (a) **명시적으로 규정** (b) **침묵·중립**(규정 없음) (c) **상반** 중 어디인지 구분해서 쓴다. "PRD대로", "명세대로"처럼 능동 근거로 인용하는 표현은 **(a)일 때만** 쓴다. (b)는 "PRD와 충돌하지 않음"/"PRD에 관련 규정 없음"으로, (c)는 상반 사실을 그대로 적는다. 답변란·추천안을 확정하기 직전, 같은 문서의 `조사 근거`/현황표 블록과 문구가 일치하는지 1회 대조한다.
7-4. 기술 구현 방식(예: 3D 뷰어 구성, 데이터 반영 방식, 라이브러리 선택)을 사람에게 물을 때, 선택지를 스스로 재구성하면서 `01-prior-art.md`에 이미 조사된 직접 관련 선례를 빠뜨리지 않는다. 질문을 만들기 전에 관련 `01-prior-art.md` 섹션을 다시 확인하고, 거기 기술된 선례 기법이 있으면 그 기법을 있는 그대로(단순화하지 않고) 선택지 중 하나로 포함한다. "더 단순해 보이는" 대안만 제시하면 사람의 답변은 선례를 알고 내린 결정이 아니라 좁은 메뉴 안에서 고른 결정이 된다.
8. T04 시작 전, 신규 디렉토리 생성이 필요하면 정확한 경로를 사람에게 재확인한다. 계획에 신규 라이브러리 추가가 있는데 `02-decisions.md`에서 사람 승인을 받지 않았으면 T04를 시작하지 않는다.
8-1. T05 시작 전, UI 변경이 포함된 작업이면 dev 서버가 떠 있는지 확인하고, 떠 있지 않으면 먼저 띄운다. T05 완료 후에도 dev 서버를 임의로 끄지 않는다 - Orchestrator가 직접 확인차 켰던 서버라도 검증자 실행 전에 끄지 않는다. 포트 충돌 등 구체적으로 꺼야 할 이유가 생기거나 사용자가 명시적으로 요청할 때만 종료한다.
8-2. 리뷰어나 구현 담당자에게 특정 우려사항이나 재검증·재수정을 위임할 때는 "이 항목만 확인"처럼 닫힌 목록으로 지시하지 않는다. 이번 수정이 속한 변경 카테고리(예: 속성값 조정 vs DOM 구조 재배치 vs 신규 선택자 추가)를 먼저 판단하고, 그 카테고리에 이미 상시 체크리스트로 존재하는 위험(예: 구조 변경 → 오버플로/반응형 검사, 라이브러리 override → 기본 클래스 전수 대조)을 "최소 다음을 포함해, 당신의 표준 체크리스트 중 [카테고리]에 해당하는 항목도 함께 수행"처럼 열린 형태로 지시문에 넣는다. 닫힌 목록은 `integration-reviewer` 명세에 이미 있는 포괄적 검증 의무(고정 치수 실측 등)를 사실상 대체해버린다.
8-3. Orchestrator가 산출물의 시각 표현(색·배경·테두리 등 스타일 형용사: "다크 버튼", "회색 배경" 등)을 팀원 지시문이나 사용자 보고로 옮길 때는, 그 값에 Figma 원문 근거(노드 ID + 토큰명 또는 hex)가 동반돼 있는지 먼저 확인한다. 근거가 없으면 (a) 지시문에는 "(계획서 시각 추정 - 해당 노드 원문으로 재확인 필요)"를 붙여 전달하고, (b) 사용자 보고에서는 그 스타일을 단정형으로 쓰지 않는다("계획서상 ~로 보이나 미확정"). 이 규칙은 색상에 한정되지 않는다. `04-review.md` 등의 "영향 범위"/구현 대상 목록을 지시문으로 옮길 때는, 값 라벨 유무·간격·구조 등 어떤 속성이든 근거로 인용된 문구(노드 설명, 콘텐츠명)가 지시 대상 콘텐츠명과 정확히 같은지 대조한다. 다르면 그대로 전달하지 않고 근거를 재조회한 뒤에만 전달한다.
8-4. integration-reviewer가 "토큰 초과로 확인 불가"나 "저장 파일에 노드 없음"을 `04-review.md`의 "확인 못한 부분"으로 보고하면, 1-1단계의 하위 노드 쪼개기 저장을 실제로 시도했는지 먼저 확인한다. 시도하지 않았으면 Orchestrator가 하위 노드를 저장하고 재검증을 요청한 뒤에만 그 항목을 "확인 못한 부분"으로 사람에게 보고한다.
9. **T05 완료 후, `artifacts/feature-team/04-review.md`를 읽고 그대로 사람에게 전달하지 않는다.** 서브에이전트의 요약은 실제로 한 일이 아니라 하려던 일을 설명할 뿐이므로, 위험 기반(risk-based)으로 재검증한다. 고정 개수를 채우는 방식이 아니라 아래 기준에 해당하는 항목을 우선순위로 직접 재현해서 확인한다.
   - 되돌리기 어렵거나 사람이 바로 다음 결정(커밋·배포 승인 등)을 쌓을 항목 - 최우선.
   - 지금 확인하지 않으면 나중엔 재현이 더 어려워지는 항목(예: dev 서버가 꺼지면 못 보는 렌더링, 이번 세션에서만 가능한 상태).
   - 서술이 구체적이고 그럴듯하지만 실제로는 주관적 판단이 섞인 주장("rules와 일치", "구조가 맞다", "레이아웃이 Figma와 일치", "정책에 부합") - 검증 없이 넘어가기 가장 쉽고 틀리기도 쉽다.
   - "요소 존재"와 "시각적 일치"는 별개 검증축이다. "일치"라고 사람에게 보고하려면, 보고 대상으로 언급한 속성(색상·패딩·폰트 크기·집계 수치 등) 또는 "검증 완료"로 표시한 노드마다 각각 `getBoundingClientRect`/`getComputedStyle` 같은 실측값이나 원문의 정확한 px/색상 토큰, 화면 계산 결과와 목데이터 원본 대조를 남긴다 - 하나만 대조하고 나머지를 같은 "일치"로 묶지 않는다. 대조하지 못한 속성이나 노드는 "확인 못한 부분"으로 따로 명시한다. 두 값이 "일치/거의 같다"는 결론에는 계산 근거(알파 합성, 단위 환산 등)를 함께 제시한다. 이 규칙은 리뷰어의 보고뿐 아니라 **Orchestrator 자신의 재검증에도 동일하게 적용된다** - 스크린샷을 찍었다는 사실 자체가 검증을 마쳤다는 뜻은 아니다.
   - 컨테이너의 배경/테두리/그림자("요소 형태")는 텍스트 스타일과 별개 축이다 - 텍스트·아이콘 일치만으로 넘어가지 않는다.
   - 코드 주장(예: "X 파일 미변경")은 `grep`/`git status`/`git diff`로, 렌더링 주장은 실제 재현(스크린샷/콘솔 로그 재확인)으로, 타입/린트 통과 주장은 재실행으로 직접 확인한다. 구현 노트에 "마크업 유지"/"변경 없음"처럼 단정하는 문구가 있는 파일은 최우선 재검증 대상이다.
   - 여러 variant가 같은 컴포넌트/헬퍼를 공유하는 구조는, 헬퍼 파라미터가 variant별로 실제로 차별화됐는지가 그 자체로 고위험 재검증 대상이다.
   - 반복형 하위 구조(범례 그리드, 배지열 등)는 "개수가 맞다"와 "그 폭 비율·줄바꿈 지점이 맞다"가 별개 검증축이다. `00-figma-metadata.md`가 있으면 그 수치와 실제 렌더링의 `getBoundingClientRect()`를 직접 대조한다.
   - `00-figma-geometry.md`가 있으면 `04-review.md`의 "Figma 기하 실측 증거"에서 실제 가시 요소별 selector, 기준값, 실측값, 판정, 근거가 모두 남았는지 확인한다. 부모 컨테이너 측정만 남아 있거나 미측정 항목을 통과로 처리했으면 T05 완료로 인정하지 않는다.
   - "사용 여부"와 "정확성"은 서로 다른 질문이다. `grep`으로 "쓰이는 곳이 없다"를 확인한 것은 그 코드가 제대로 구현됐는지까지 확인한 것이 아니다 - 사용 여부만 확인하고 정확성에 대한 판단까지 사람에게 확언하지 않는다.
   - 검증 기준은 행위의 가역성이 아니라 주장의 확신도에 맞춘다. "어차피 삭제할 코드", "git 이력에 남으니 되돌릴 수 있다"는 이유로 검증을 생략하지 않는다 - 사람에게 하는 모든 확언은 그 확언 자체가 검증 대상이다.
   - 리뷰어 자신의 위험/확신 평가 문구("기존 패턴이라 위험 낮다", "이미 검증된 패턴이라 별도 실측 없이도 안전")는 근거가 아니라 재검증 대상 주장이다. Orchestrator가 이미 확보한 정보와 상충하지 않는지 대조하고, 뒷받침할 근거가 없으면 그 판단을 신뢰하지 않는다. 재검증 테스트를 설계할 때 결과가 항상 통과하도록(예: 컨텐츠 고정폭에 뷰포트를 정확히 맞추는 식으로) 조건을 고르지 않는다 - 실제로 틀릴 수 있는 조건에서 테스트해야 검증이다.
   - "사람 승인 필요"·"수정 필요" 항목 중 Orchestrator가 직접 수정을 적용한 항목이 있더라도, 그 사실이 문서의 나머지 항목까지 검증됐다는 근거가 되지 않는다.
   - 재검증한 항목 중 하나라도 `04-review.md` 내용과 다르면, 그 즉시 검증 범위를 넓혀 나머지 "통과" 항목도 마저 재현 확인한다. 차이(추가 결함, 또는 "확인 못한 부분"이 실제로는 재현되지 않음 등)는 문서에 갱신하고 사람에게 그대로 보고한다.
   - 이 재검증을 마친 뒤에만 사람에게 요약 보고하고, "사람 승인 필요" 항목에 대한 확인을 받는다. "확인 못한 부분"은 "통과"와 동일한 비중으로, 생략·축소 없이 그대로 전달한다.
10. `artifacts/feature-team/improvement-log.md`를 갱신한다.
11. 작업 종료 시 이번 실행에서 스폰한 모든 팀원을 `TaskStop`(`task_id`에 팀원 이름)으로 실제로 종료시킨다. `SendMessage`로 마무리를 알리는 것만으로는 팀원 프로세스가 종료되지 않고 idle 상태로 남는다 - `SendMessage`는 완료로 치지 않는다. 이 정리를 생략하면 다음 실행에서 같은 이름 재스폰 시 접미사 충돌이 난다.
12. T01~T05 사이클이 끝난 뒤 Orchestrator가 직접 소스를 후속 수정할 때도, 배치·간격 분배처럼 여러 해석이 가능한 시각적 결정은 Figma 스크린샷(`00-figma-screenshot.png` 또는 재조회 스크린샷)과 대조하기 전에는 "완료"로 보고하지 않는다. 수치(예: 높이)가 맞았다는 것과 그 수치 안의 배치 방식이 맞았다는 것은 별개 검증축이다.
13. Orchestrator가 서브에이전트 위임 없이 검증 작업을 직접 수행해 "완료"로 기록할 때는(실행 방식 전환 승인을 받은 경우), 확인한 범위(브라우저 렌더링만 확인했는지, Figma 원문 재대조를 포함했는지, 사용한 도구)를 완료 사유에 반드시 함께 적는다. 범위를 밝히지 않은 완료 보고는 팀 통신 프로토콜 위반으로 본다.

## 도구 미연결 처리

- 팀원이 필요한 도구나 근거 자료(Figma 원문 등)가 없다고 `SendMessage`로 알리면, Orchestrator는 작업 전체를 멈추지 않고 사람에게 디자인 링크/캡처나 필요한 자료를 직접 요청한다. 받은 대체 자료로 해당 Task를 이어서 진행한다.
- **이 알림은 반드시 작업 도중, 발견 시점에 와야 한다.** 팀원의 완료 보고에서야 "도구가 없어 일부 사양을 임의로 추정해 구현했다"는 내용이 처음 나오면 팀 통신 프로토콜 위반이다 - 그 결과물(추정에 기반한 부분)을 확정된 것으로 취급하지 않는다. 즉시 사람에게 이 사실을 보고하고, 재작업 여부(롤백 후 대체 자료로 재구현할지, 그대로 승인할지)를 사람이 결정하게 한다.

## 사람 승인 지점

- 이번 작업의 Figma 타겟 노드 (UI 작업이면 매 작업 확인)
- `artifacts/feature-team/02-decisions.md`의 확인 필요 항목 (API 통신 방식, 백엔드 미확정 엔드포인트, 신규 디렉토리 위치 등)
- 신규 라이브러리 추가 여부
- 신규 디렉토리 생성 위치
- 도구 미연결 시 대체 진행 방식
- `artifacts/feature-team/04-review.md`의 "사람 승인 필요" 항목
- 실행 방식 전환 (서브에이전트 위임 → Orchestrator 직접 수행, 또는 그 반대). **이 승인은 다른 승인(예: "N건 수정 진행할까요?")에 자동으로 포함되지 않는다.** Orchestrator가 `src/` 파일을 직접 Edit/Write하거나 팀원 몫의 검증을 직접 하려는 시점 자체가 트리거이며, 그 직전에 "이 작업을 제가 직접 할까요, 담당 팀원에게 위임할까요?"를 별도 질문으로 명시적으로 묻고 답변을 받은 뒤에만 진행한다. 사용자의 일반 승인("진행해"/"ㄱㄱ" 등)을 실행 방식 승인으로 확대 해석하지 않는다. 판단 기준은 "쓰기냐 읽기냐"가 아니라 "Agent Team 구성표에 이 일을 맡을 역할이 이미 있느냐"다 - Figma 원문 재대조·PRD 정량 정책 대조·교차 검증은 integration-reviewer의 책임이므로, Orchestrator가 같은 도구를 갖고 있어도 대신 수행하지 않는다. 구성표에 담당자가 없는 일(Task 상태 확인, 사람에게 질문, Figma 원문 저장)은 원래 Orchestrator 몫이라 트리거가 아니다.
- git commit/push, 파일 삭제 (`AGENTS.md` "고위험 행동 차단" 그대로 적용)

## 실패 처리

- 입력이 부족하면 바로 진행하지 말고 빠진 정보를 질문한다.
- 팀원 1명이 실패하면 먼저 실패 원인이 태스크 자체(계획 불일치, 확인 필요 항목 미해소 등)인지 도구/환경/계정 한도 등 시스템 차원인지 분류한다.
  - 태스크 자체의 문제로 판단되면 `TaskGet`으로 상태를 확인하고 `SendMessage`로 1회 재시도 또는 재할당을 지시한다.
  - 시스템 차원일 수 있다고 판단되면, 그 판단이 추정임을 먼저 사용자에게 보고하고 확인을 받은 뒤에만 실행 방식(재시도 / 대체 접근 / 중단)을 바꾼다 - 확인 없이 서브에이전트 위임을 포기하고 Orchestrator가 직접 구현으로 전환하지 않는다.
- 과반 작업이 실패하면 현재 상태, 남은 위험, 선택지를 사용자에게 보고하고 확인을 받는다.
- 충돌하는 결과는 삭제하지 않고 출처와 근거를 병기한 뒤 사람이 판단하게 한다.
- 신규 디렉토리 생성, 기존 코드 대량 수정처럼 되돌리기 어려운 작업은 사람 승인 전 완료하지 않는다.
- 재시도가 동일 원인으로 다시 실패하면, 관측된 실패 사유를 추측 없이 그대로 사용자에게 전달하고 다음 행동을 사용자가 선택하게 한다.
