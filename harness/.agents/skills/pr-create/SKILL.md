# PR 생성

## 입력과 권한

- 현재 저장소의 개발·Git 규칙과 PR 템플릿을 먼저 확인.
- 사용자가 지정한 대표 커밋을 제목·본문의 기준으로 사용. 특정 해시·계정·저장소를 공용 규칙에 고정하지 않음.
- 초안 요청은 작성까지만, PR 생성 요청은 생성까지 진행. 명시적인 생성 요청이 있으면 중복 승인 없이 실행하되 저장소에서 별도로 요구하는 승인 절차는 준수.
- 커밋·push·rebase·병합·리뷰어 요청·라벨 신규 생성은 별도 요청 없이 실행하지 않음. PR 생성 승인을 해당 작업의 승인으로 확대하지 않음.

## 변경과 대상 확인

1. `git status --short --branch`, `git branch --show-current`, `git remote -v`로 작업 트리·브랜치·저장소 확인. 미커밋 변경은 PR에 포함되지 않음을 알리고 기존 작업 보존.
2. GitHub 연결 도구가 충분하면 우선 사용하고, 없으면 `gh` 사용. CLI 예시:
   - `gh api user --jq .login`: 인증 계정 확인. "나"는 확인한 사용자 계정이며 Assignee에는 `@me` 사용. 계정이 사용자 지정과 다르면 임의 전환 없이 확인.
   - `gh repo view --json nameWithOwner,defaultBranchRef`: 실제 대상 저장소·기본 브랜치 확인.
   - 로그인 성공과 저장소 접근 권한을 구분. sandbox·네트워크·키체인 접근 오류는 해당 실행 권한 문제부터 확인하고, 저장소 조회 실패를 곧바로 로그아웃이나 토큰 만료로 단정하지 않음. 자격 증명 값 출력 금지.
3. base는 사용자 지정 → 프로젝트 통합 브랜치 → GitHub 기본 브랜치 순서로 결정. head는 현재 작업 브랜치로 명시. detached HEAD, base와 head 동일, 저장소 불일치 또는 접근 실패면 게시를 중단하고 근거와 필요한 입력 보고.
4. 원격 base/head의 최신 상태를 확인하고 필요하면 fetch. `git log --format=fuller <base-ref>..HEAD`와 `git diff <base-ref>...HEAD`로 PR 전체 범위 확인. diff가 없으면 생성하지 않음.
   - 원격 head SHA와 로컬 HEAD도 대조. 미게시 커밋·원격 브랜치 부재·불일치가 있으면 초안까지 준비하고 push 필요 상황 보고. 자동 push 금지.
5. 대표 커밋은 사용자가 지정한 해시 우선. `git show`와 브랜치 포함 여부를 확인하고, base에 이미 들어간 커밋이면 작성 기준으로 적합한지 확인.
   - 미지정이면 base 이후 커밋의 제목·본문·diff를 읽고 제품 변경을 대표하는 커밋 선택. 하네스 동기화·작업 기록 커밋을 단순히 최신이라는 이유로 선택하지 않음.
   - 서로 독립적인 제품 커밋이 여러 개여서 대표를 정할 수 없으면 후보를 보여주고 확인. 브랜치 전체 diff를 특정 커밋 diff로 대신하지 않음.
6. 같은 저장소의 base/head에 열린 PR이 있는지 조회. 예: `gh pr list --repo OWNER/REPO --base BASE --head HEAD --state open --json number,title,url`.
   - 이미 있으면 중복 생성하지 않고 해당 PR을 읽음. 갱신 요청이면 요청한 필드만 갱신하고, 생성만 요청했으면 기존 URL을 보고.
   - fork에서는 원본 저장소와 head 소유자도 대조해 동명의 다른 브랜치와 구분.

## 제목·본문·메타데이터 작성

- 제목은 대표 커밋 제목을 기준으로 티켓 번호·종류·의미 보존. 사용자 지정 제목과 저장소 PR 제목 규칙이 있으면 우선 적용.
- 대표 커밋 본문을 의미 단위로 정리하고 전체 브랜치 diff와 대조. 실제 추가 변경은 보완하고 더 이상 맞지 않는 설명은 수정.
- 변경 목적과 사용자에게 나타나는 동작을 먼저 설명. 파일 목록·작업 경위·산출물 갱신을 기계적으로 나열하지 않음.
- 하네스 변경 등 부수 변경이 PR에 포함되면 영향이 드러날 만큼 따로 기재. 대표 커밋 외 변경을 무조건 누락하지 않음.
- 저장소 PR 템플릿을 우선 적용. 템플릿이 없으면 아래 구조를 변경 규모에 맞게 사용:

```markdown
## 변경 목적
해결할 문제와 변경 후 동작

## 주요 변경
- 실제 변경을 의미 단위로 요약

## 검증
- 실행한 명령과 확인된 결과

## 남은 제약
- 실제로 남은 제약이나 미검증 항목
```

- 검증 결과는 현재 코드에 유효한 실행 증거만 사용. 실행하지 않은 검사는 통과로 표시하지 않고 정적 검사·브라우저·실제 API 검증을 구분. 추가 변경 없는 검사를 본문 작성 때문에 반복하지 않음.
- 한국어로 작성. 내부 메모리 인용, 인증 정보, 실행하지 않은 검증 결과를 PR 본문에 넣지 않음.
- 실제 목록을 조회하고 기존 라벨의 설명과 변경을 대조. 예: `gh label list --repo OWNER/REPO --limit 100 --json name,description`. 목록이 잘리면 후속 페이지까지 확인.
  - 기능 추가는 `enhancement`, 버그 수정은 `bug`, 문서 작업은 문서 라벨처럼 의미가 맞는 기존 라벨을 최소한으로 선택. 이름이 같아도 저장소 설명과 다르면 사용하지 않음.
  - 적절한 라벨이 없으면 임의 생성하지 않고 라벨 없이 진행한 이유 보고.
- Assignee는 확인한 본인으로 지정. Reviewer와 혼동하지 않음. 기존 PR 갱신 시 타인의 담당자·라벨을 임의 제거하지 않음.

## 저장·게시·확인

1. `artifacts/pr-create/<head의 슬래시를 하이픈으로 바꾼 이름>/body.md`에 최종 본문 저장. 같은 폴더의 `result.md`에 저장소, base/head, 비교 SHA, 대표 커밋, 제목, Assignee, 라벨, 게시 여부·URL, 검증 근거 기록.
   - 기존 기록이 있으면 먼저 읽고 동일 PR 작업인지 확인. 재실행에서는 기록만 믿지 않고 GitHub의 현재 상태 재조회.
   - 본문과 메타데이터를 대조한 뒤 사용자 요청에 따라 초안 또는 게시로 종료. 실제 게시 내용은 이 파일에서 읽음.
2. CLI 게시 예시에서 각 값을 실제 확인한 값으로 대체하고 셸 인자를 안전하게 인용. 선택한 라벨이 없으면 `--label` 생략:

```sh
gh pr create --repo OWNER/REPO --base BASE --head HEAD \
  --title '대표 커밋 기반 제목' --body-file 'artifacts/pr-create/HEAD/body.md' \
  --assignee '@me' --label '실제 기존 라벨'
```

   - `--repo`, `--base`, `--head`를 명시해 저장소·대상을 고정하고 암묵적인 push/fork 방지. `--fill`로 전체 커밋 메시지를 무검토 복사하지 않음.
   - 게시 없는 검증에 `gh pr create --dry-run`을 사용하지 않음. 이 옵션도 push할 수 있으므로 초안 파일과 조회 명령으로 검증.
   - draft 요청이면 `--draft` 추가. 기존 PR 갱신은 승인된 범위에 한해 `gh pr edit`와 `--body-file`, `--add-assignee '@me'`, `--add-label` 사용.
3. 생성 후 `gh pr view URL --repo OWNER/REPO --json url,title,body,baseRefName,headRefName,assignees,labels`로 실제 제목·본문·대상·담당자·라벨 확인하고 결과 기록 갱신.
   - 명령이 실패하거나 응답이 끊겨도 곧바로 재생성하지 않음. 같은 base/head의 PR 존재 여부부터 재조회하고 이미 생성된 PR을 기준으로 복구.
   - 생성은 성공했지만 메타데이터가 누락되면 같은 PR에 요청된 값을 보완한 뒤 재조회. 권한 문제로 불가능하면 URL과 미완료 항목을 정확히 보고하고 완료로 표시하지 않음.
4. 최종 응답은 초안 경로 또는 PR URL, Assignee·라벨, 미검증·실패 항목을 짧게 보고.
